### 3.1 量表计分（SCALE 模块）

#### BUG-SCALE-01 · MoCA-B 满分文案不一致

#### BUG-SCALE-02 · NPI 红灯阈值无法覆盖满分 144

- **文件**：`src/utils/prototypeScales.ts:459`（NPI 红灯阈值）
- **改动**：经核查当前代码阈值已为 `{ min: 13, max: 999, level: "red", label: "精神行为症状较重（NPI ≥13）…" }`。**V3.2 基础版本合并时已将该值由 99 改为 999**，本批次无需改动。
- **原因**：原 `max:99` 使满分 144 落入"未匹配阈值"兜底；TC-SCALE-09 / TC-SCALE-12 复现。
- **影响范围**：NPI 满分亮红灯现已正确；关联用例可直接回归通过。

#### BUG-SCALE-03 · MoCA-B 双计分逻辑，未作答时不一致（0 分 vs 23 分）

- **文件**：`src/components/AiAnalysisModal.tsx`（核心修改点 + `src/utils/scoringCalculators.ts` 复用）
- **改动**：删除内联求和与 `|| 23` 兜底，改为调用统一的 `calculateMoCAB`；未作答时记为 `null` 并显式标注"未评估"：

  ```ts
  import { calculateMoCAB } from "../utils/scoringCalculators";
  // 删除：const mocaScore = (moca?.executiveTrail||0)+…+(moca?.attentionDigitsBlack||0) || 23;
  const mocaAnyFilled = moca && Object.values(moca).some((v) => v != null && Number(v) !== 0);
  const mocaScore = mocaAnyFilled ? calculateMoCAB(moca, edu).score : null;
  const mocaStr = (bound, mode) =>
    mocaScore === null ? "未评估"
      : mode === "max" ? String(Math.max(mocaScore, bound)) : String(Math.min(mocaScore, bound));
  // 报告 4 个分型 summary/keyAbnormalities 中的 Math.max(mocaScore,24)/Math.min(mocaScore,20) 等
  // 全部替换为 mocaStr(24,"max") / mocaStr(20,"min") 等，空值时显示"未评估"
  ```
- **原因**：空输入时主函数算 0 分，AI 内联 `|| 23` 把 0 兜底成 23，伪造"认知正常"，与综合报告/导出层 0 分判定矛盾，可能误导医生；TC-SCALE-05 / 批次9 验证确认。
- **影响范围**：AI 研判报告中 MoCA-B 展示口径与 `calculateMoCAB` 完全一致；空白患者不再显示伪造分数。

## 四、后端 / 构建缺陷修复（逐文件）

### 4.1 数据库与配置（SECURITY / OTHER-04 / API / DB 模块）

#### BUG-SECURITY-01 · 数据库 token 硬编码

- **文件**：`server/turso.ts`
- **改动**：删除 `DEFAULT_TURSO_URL` / `DEFAULT_TURSO_TOKEN` 硬编码常量，改为仅从环境变量读取；`getTursoClient()` 惰性初始化（见下条）。
- **原因**：完整 JWT 写死在源码，提交版本控制即泄露，任何人可直连库读写全部患者数据；TC-API-11 关联。
- **影响范围**：彻底移除源码内凭证；数据库地址/token 改由 `.env` 或启动环境变量注入。

#### BUG-OTHER-04 · .env 加载顺序导致配置不生效

- **文件**：`server/turso.ts`（`getTursoClient` 惰性初始化）
- **改动**：

  ```ts
  let clientInstance: Client | null = null;
  export function getTursoClient(): Client {
    if (!clientInstance) {
      const tursoUrl = process.env.TURSO_DATABASE_URL;     // 首次调用时才读 env
      const tursoToken = process.env.TURSO_AUTH_TOKEN;
      if (!tursoUrl) throw new Error("TURSO_DATABASE_URL 未配置…");
      clientInstance = createClient({ url: tursoUrl, authToken: tursoToken });
    }
    return clientInstance;
  }
  ```
- **原因**：原顶层 `import` 阶段读 env 早于 `server.ts` 的 `dotenv.config()`，`.env` 永远不生效；**若不修此缺陷，BUG-SECURITY-01 移除硬编码后无默认值将直接连库失败**。两条必须一起修。
- **影响范围**：`.env` 配置现可生效；本地离线库启动命令（见 §六）。

#### BUG-API-01 · 云端 drafts 表缺 flow_id 列，多流草稿隔离不可用

- **文件**：`server/turso.ts`（`initDatabase` 内 drafts 建表逻辑）
- **改动**：增加结构检测与惰性迁移——表不存在则建三列主键新表；已存在且无 `flow_id` 三列索引则 `RENAME→建新表→去重迁移→DROP 旧表`；迁移失败回退保留旧表。
- **原因**：代码 DDL 已定义 `(patient_id, role, flow_id)` 三列主键，但 `CREATE TABLE IF NOT EXISTS` 不迁移旧云端表（仍是两列），同患者第二份草稿触发 UNIQUE 约束失败 500；TC-API-06 复现。
- **影响范围**：后端多流程草稿（受试者/家属/医生并行续聊）隔离恢复可用；单份草稿行为不变。

#### BUG-DB-01 · 启动自动清库风险

- **文件**：`server.ts`（`initDatabase` 启动播种逻辑）
- **改动**：

  ```ts
  const seedOnBoot = process.env.SEED_ON_BOOT === "true";
  if (seedOnBoot) {
    console.log("[DB] SEED_ON_BOOT=true：即将清空并重置为标准 4 位受试者队列…");
    await cleanAndSeedStandardCohort();
  } else {
    console.log(`[DB] 检测到已有 ${currentPatients.length} 位受试者数据，跳过自动播种…`);
  }
  ```
- **原因**：原实现按"非标准队列/脏数据"启发式每次启动自动清库重播种，多人共用云库时他人数据被清空；TC-API-01/02 关联。
- **影响范围**：默认启动不再自动清库；需重置时显式设 `SEED_ON_BOOT=true` 或调 `POST /api/v1/reset-cohort`。

#### BUG-DB-02 · documents / notifications 表缺失

- **文件**：`server/turso.ts`（`initDatabase` 内）
- **改动**：补齐规范（接口与数据表定义文档 §3(5)）声明但未落地的 `documents`、`notifications` 两张表结构（CREATE TABLE IF NOT EXISTS）。
- **原因**：OCR 解析来源、医生确认动作、AI 待审核消息无后端落库表，无法完整追溯。
- **影响范围**：表结构就绪；应用层写入/读取接口留待后续迭代接入（本批次仅建表，不破坏既有 4 表行为）。

#### BUG-OTHER-03 · 类型配置缺失 + tsc 清零

- **文件**：`package.json` + `tsconfig.json`
- **改动**：
  - `package.json` devDependencies 补 `"@types/react": "^19.0.0"`、`"@types/react-dom": "^19.0.0"`。
  - `tsconfig.json` 增加 `"noImplicitAny": true`、`"strictFunctionTypes": true`（保留 `skipLibCheck` / `moduleResolution: bundler` / `isolatedModules`）。
  - **未开启完整 `strict: true`**：全量 strict（含 `strictNullChecks`）会在既有代码库引发大量 null 相关报错；缺陷清单本身建议"分模块推进或先开 `strictFunctionTypes/noImplicitAny` 级别"，故采用缺陷认可的子集。
- **原因**：原项目缺 React 类型声明，组件 Props 全解析为 any，必需 prop 缺失（如 BUG-SCALE-04）不被拦截；B.1 静态检查"tsc 0 错误"不成立。
- **影响范围**：类型检查覆盖度显著提升；通过 §三.4 的中央类型补全 + 逐文件修正，将错误从 90 条清零至 0。

### 4.2 AI / OCR（AI / OCR 模块）

#### BUG-AI-01 · 无效 Gemini Key 时 analyze-assessment 返回 500

- **文件**：`server.ts`（`/api/ai/analyze-assessment` 路由）
- **改动**：把 `const { patientData, assessmentSummary } = req.body;` 从 try 内移至 try 外（catch 降级需访问入参）；catch 分支返回规则库分析结果而非 500：

  ```ts
  app.post("/api/ai/analyze-assessment", async (req, res) => {
    const { patientData, assessmentSummary } = req.body;   // 移到 try 外
    try { const ai = getGeminiClient(); /* 真实调用 */ }
    catch (error: any) {
      return res.json({ success: true, isAiGenerated: false,
        analysis: generateRuleBasedAnalysis(patientData, assessmentSummary),
        model: GEMINI_MODEL });
    }
  });
  ```
- **原因**：占位符 key 被传入 GoogleGenAI，API 调用失败直接 500；与 `clinical-reasoning` 端点降级行为不一致；TC-AI-07 复现。
- **影响范围**：无真实 key 时该端点优雅降级，前端永不崩溃。

#### BUG-AI-04 · 模型名不存在 `gemini-3.7-flash`

#### BUG-AI-03 · 缺数据用默认值伪装成"有结论"

- **改动**：缺失量表不再用 `?? 28 / ?? 25 / ?? 0` 当作"正常/满分"默认值，统一为 `null`，并在报告文本中标注"未评估/数据缺失"。

## 六、本地验证注意事项（环境现象，非代码阻断）

1. **本地 `file:` 库启动命令**（绕过 .env 不生效的历史坑，亦适用于无网络环境）：

   ```powershell
   cd ad-ouc-system
   TURSO_DATABASE_URL="file:./local-dev.db" TURSO_AUTH_TOKEN=dummy npm run dev
   ```
2. **`SQLITE_READONLY` 现象**：若本地 `local-dev.db` 文件只读（如被其他进程占用或权限限制），drafts 迁移阶段 `ALTER TABLE ... RENAME` 写操作会报 `SQLITE_READONLY`。**解决**：删除 `local-dev.db` 后重启（迁移会重建新结构）。
3. **`EADDRINUSE :3000`**：上次未正常关闭的开发服务器仍占用端口。启动前确认无残留 `node` 进程，或用其他端口。
4. **云库默认共享演示库**：测试写入会留痕；如需隔离请用本地 `file:` 库（已加入 `.gitignore`）。
5. **`npm run dev` 在无真实 `GEMINI_API_KEY` / `PADDLE_OCR_TOKEN` 时正常降级**：AI 研判 / 综合量表分析 / OCR 解析均走规则引擎或演示数据，三端流程与核心量表不受影响（已在冒烟中验证 `isAiGenerated:false`）。
